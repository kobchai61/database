สไลด์ 7

Update Anomaly

UPDATE Books SET BorrowerAddress = '789 Oak St, Newtown, USA'
WHERE BorrowerName = 'John Smith';
-- Query OK, 0 rows affected · Rows matched: 2  Changed: 0

การเปลี่ยนที่อยู่ของผู้ยืมคนเดียวต้องแก้ หลายแถว ในสไลด์ "Rows matched: 2" แปลว่ามี 2 แถวที่ต้องแก้ (Changed: 0 เพราะค่าที่ใส่เท่ากับค่าเดิมพอดี)

ตัวอย่าง: ทำไมเป็นปัญหา

ถ้าเจ้าหน้าที่แก้ด้วย WHERE BookID = 1 แทน ที่อยู่ John Smith จะเปลี่ยนแค่แถว 1 แถว 2 ยังเป็นที่อยู่เก่า ระบบเดียวมีที่อยู่ John Smith สองค่าที่ขัดกัน นี่คือ inconsistency ที่ update anomaly ทำให้เกิด

Insertion Anomaly

INSERT INTO Books (BookID, BorrowerName, BorrowerAddress)
VALUES (6, 'Emma Watson', '321 Pine St, Hollywood, USA');

คำสั่งนี้รันผ่าน ได้แถว 6 | NULL | NULL | Emma Watson | 321 Pine St... คือมี "หนังสือ" ที่ไม่มีชื่อและผู้แต่ง เพราะอยากบันทึกผู้ยืมคนใหม่แต่ตารางบังคับให้ข้อมูลผู้ยืมต้องอยู่ในแถวหนังสือ ในทางกลับกัน หนังสือที่ยังไม่มีคนยืม (BookID 4) ก็ต้องใส่ NULL ในช่องผู้ยืม

สรุป: insertion anomaly คือเพิ่มข้อมูลของสิ่งหนึ่งไม่ได้อย่างถูกต้อง ถ้าไม่มีข้อมูลของอีกสิ่งหนึ่ง

สไลด์ 16–19

Functional Dependency คืออะไร

FD เป็น constraint ระหว่างเซตของ attribute สองเซตใน relation เขียน X → Y อ่านว่า "X กำหนด Y" หมายความว่า ค่า X แต่ละค่าจับคู่กับค่า Y ได้ค่าเดียวเท่านั้น FD เป็นรากฐานของ normalization

  • เป็นคุณสมบัติจาก ความหมาย (semantics) ของ attribute ไม่ได้มาจากข้อมูลที่บังเอิญมีอยู่
  • ต้อง hold กับ ทุก relation instance ที่เป็นไปได้
  • หมายถึงค่าของบาง attribute ระบุค่าของ attribute อื่นได้แน่นอน
ตัวอย่างจากสไลด์ 19

Student(StudentID, Name, DateOfBirth) มี StudentID → Name, DateOfBirth คือรหัสนักศึกษาหนึ่งรหัสมีชื่อเดียวและวันเกิดเดียว แต่ Name → StudentID ไม่ hold เพราะคนชื่อซ้ำกันได้

FD เกี่ยวกับการออกแบบที่ดีอย่างไร (1/8–7/8)

  1. ระบุความสัมพันธ์ของข้อมูล ช่วยตัดสินว่า attribute ไหนควรอยู่ตารางเดียวกัน หา key และเข้าใจ business rule · ตัวอย่าง Students(StudentID, Name, SectionID, SectionName, Professor) มี StudentID → Name และ SectionID → SectionName, Professor แปลว่าข้อมูล section ไม่ได้ขึ้นกับนักศึกษา ควรแยกออก
  2. ลด redundancy เห็นข้อมูลที่ซ้ำ แล้วแยก attribute ไปคนละ relation ตาม dependency ทำให้ได้ normal form สูงขึ้น
  3. รักษา integrity หา key ที่ถูกต้อง ลด anomaly ทั้งสามแบบ ข้อมูลแต่ละชิ้นอยู่ที่เดียว
  4. ตัวอย่างสไลด์ 24–25: Students(StudentID, Name, Major, Department) มี StudentID → Major และ Major → Department ปัญหา: "Computer Science Department" ซ้ำทุกคนที่เรียน CS, ภาควิชาเปลี่ยนชื่อต้องแก้หลายร้อยแถว, บางแถวอาจเขียน "Comp Sci Dept" ไม่ตรงกัน · แก้เป็น Students(StudentID, Name, Major) + Majors(Major, Department) ชื่อภาคเก็บครั้งเดียวต่อสาขา และตัด transitive dependency StudentID → Department (ผ่าน Major)
  5. ช่วย normalization (สไลด์ 26): 1NF ตัด repeating group/ค่าไม่ atomic · 2NF ตัด partial dependency (non-key ขึ้นกับส่วนหนึ่งของ composite key) · 3NF ตัด transitive dependency (A → B → C) · BCNF ทุก determinant ต้องเป็น candidate key

สไลด์ 31–33

Lossless vs Lossy (นิยามทางการ)

Lossless: แยก R เป็น R1, R2 แล้ว join กลับได้ตารางเดิมเป๊ะ ไม่หาย ไม่เกิน

Lossless:  ∏R1(r) ⋈ ∏R2(r) = r
Lossy:     r ⊂ ∏R1(r) ⋈ ∏R2(r)     (ผล join ใหญ่กว่า r เพราะมี spurious tuples)
r = instance ของ R · ∏ = projection (เลือกคอลัมน์) · ⋈ = natural join
สไลด์ 33: R = (A, B, C), R1 = (A, B), R2 = (B, C)
r            ∏A,B(r)    ∏B,C(r)      ∏A,B(r) ⋈ ∏B,C(r)
A  B  C      A  B       B  C         A  B  C
α  1  A      α  1       1  A         α  1  A
β  2  B      β  2       2  B         β  2  B      = r ✓ lossless

ได้เท่าเดิมเพราะ B ซึ่งเป็น attribute ร่วม ระบุแถวใน R2 ได้แถวเดียว (แต่ละค่า B มี C ค่าเดียว) เทียบกับ employee ที่ name ระบุแถวใน employee2 ได้หลายแถว

สไลด์ 34–36

Normalization Theory และ legal instance

เป้าหมาย: ตัดสินว่า R อยู่ในรูปที่ "ดี" หรือไม่ ถ้าไม่ ให้แยกเป็น {R1, …, Rn} ที่ (1) แต่ละตัวอยู่ในรูปที่ดี (2) การแยกเป็น lossless ทฤษฎีนี้ตั้งอยู่บน functional dependencies และ multivalued dependencies

ข้อมูลจริงมีกฎ เช่น นักศึกษาและอาจารย์ระบุด้วย ID, แต่ละคนมีชื่อเดียว, สังกัดภาคเดียว, ภาคมี budget เดียวและอาคารเดียว instance ที่ทำตามกฎทั้งหมดเรียก legal instance FD คือการ "generalize" แนวคิดของ key

สไลด์ 38–40

Closure F⁺, Superkey, Candidate key

F⁺ = เซตของ FD ทั้งหมดที่อนุมานได้จาก F เช่น ถ้ามี A → B และ B → C ก็ได้ A → C

Superkey

K เป็น superkey ⇔ K → R คือค่าของ K ระบุ tuple ได้ไม่ซ้ำ

Candidate key

Superkey ที่ minimal: K → R และไม่มี α ⊂ K ที่ α → R

ตัวอย่าง

Student(StudentID, Name, DateOfBirth): {StudentID} เป็น candidate key · {StudentID, Name} เป็น superkey แต่ไม่ใช่ candidate key เพราะตัด Name ออกแล้วยังเป็น superkey

สไลด์ 40: FD แสดง constraint ที่ superkey บอกไม่ได้ ใน in_dep(ID, name, salary, dept_name, building, budget) เราคาดว่า dept_name → building และ ID → building hold แต่ name → salary ไม่ควร hold (ภาคมีหลายคน และแต่ละคนเงินเดือนต่างกันได้)

สไลด์ 41–42

การใช้ FD และ Trivial FD

  1. กำหนด constraint ว่าข้อมูลแบบไหน legal
  2. ทดสอบข้อมูล instance ที่ทำตาม FD ทั้งหมดเรียกว่า satisfies F
  3. บังคับกับข้อมูลในอนาคต F holds on schema ถ้าทุก legal instance ต้อง satisfy F

Trivial FD: α → β เมื่อ β ⊆ α เป็นจริงเสมอโดยไม่ให้ข้อมูลใหม่ เช่น ID, name → ID และ name → name

Dependency Preservation

การแยกเป็น dependency preserving ถ้ากฎ (FD) เดิมทุกข้อ ตรวจได้ภายในตารางย่อยตารางเดียว ถ้าต้อง join (หรือ Cartesian product) เพื่อตรวจกฎ แปลว่าไม่ preserve

อุปมาตะกร้าผ้า: ผ้าทุกอย่างอยู่ตะกร้าเดียว กฎ "ถุงเท้าต้องมีคู่" ตรวจง่าย · ถ้าแยกเก็บแต่ถุงเท้าทั้งหมดอยู่ลิ้นชักเดียว ก็ยังตรวจกฎได้ในที่เดียว = preserving · ถ้าแยกถุงเท้าไปหลายลิ้นชัก ต้องรวบรวมก่อนตรวจ = not preserving

Conclusions
  • FD เป็นหัวใจของการออกแบบ
  • แยกตารางต้องคำนึงสองเรื่อง: lossless (เพื่อไม่ให้ข้อมูลหาย) และ dependency preservation (เพื่อบังคับ constraint ได้มีประสิทธิภาพ)
  • Normalization กำจัด insertion, update, deletion anomaly

  1. ทดสอบ superkey: คำนวณ α⁺ แล้วดูว่ามีทุก attribute ของ R ไหม
  2. ทดสอบ FD: α → β hold (อยู่ใน F⁺) ⇔ β ⊆ α⁺ ถูกและเร็ว
  3. คำนวณ F⁺: ทุก γ ⊆ R หา γ⁺ แล้วออก γ → S สำหรับทุก S ⊆ γ⁺

Fourth Normal Form (4NF)

R อยู่ใน 4NF ⇔ ทุก non-trivial multivalued dependency X →→ Y, X เป็น superkey · MVD หมายถึงค่า X แต่ละค่ามี "เซต" ของค่า Y ที่ เป็นอิสระ จาก attribute อื่น · non-trivial เมื่อ Y ไม่ว่าง ไม่เป็น subset ของ X และ X ∪ Y ไม่ใช่ attribute ทั้งหมด

BCNF ดู FD ส่วน 4NF ดู MVD (กว้างกว่า) relation ที่เป็น BCNF ยังมี redundancy ได้ถ้ามี MVD

Parameterized queries: INSERT และ SELECT

def add_user(conn, username, email, age):
    query = "INSERT INTO users (username, email, age) VALUES (%s, %s, %s)"
    cursor = conn.cursor()
    try:
        cursor.execute(query, (username, email, age))   # SQL กับค่าแยกกัน
        conn.commit()                                   # INSERT ต้อง commit
        return cursor.lastrowid                         # id ที่ AUTO_INCREMENT สร้างให้
    finally:
        cursor.close()                                  # ปิด cursor เสมอ แม้ error

def get_user(conn, username):
    query = "SELECT id, username, email, age FROM users WHERE username = %s"
    cursor = conn.cursor()
    try:
        cursor.execute(query, (username,))   # tuple 1 ตัวต้องมี comma
        return cursor.fetchone()               # tuple ของแถวแรก หรือ None
    finally:
        cursor.close()

import re
USERNAME_RE = re.compile(r"[A-Za-z0-9_]{3,20}")
EMAIL_RE = re.compile(r"[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Za-z]{2,}")

def validate_user_input(username, email, age):
    if not USERNAME_RE.fullmatch(username):
        raise ValueError("Invalid username format")
    if not EMAIL_RE.fullmatch(email):
        raise ValueError("Invalid email format")
    try:
        age = int(age)
    except (TypeError, ValueError):
        raise ValueError("Age must be a number")
    if not 0 < age < 120:
        raise ValueError("Age out of range")
    return username, email, age

ROLE_PERMISSIONS = {
    "admin":   {"salary:view", "salary:update"},
    "hr":      {"salary:view", "salary:update"},
    "manager": {"salary:view"},
    "regular": set(),
}
class User:
    def __init__(self, user_id, username, role):
        self.user_id = user_id; self.username = username; self.role = role

def has_permission(user, permission):
    if user is None:
        return False                                   # deny by default
    return permission in ROLE_PERMISSIONS.get(user.role, set())

def load_user(conn, username):
    cursor = conn.cursor()
    try:
        cursor.execute("SELECT id, username, role FROM app_users WHERE username = %s", (username,))
        row = cursor.fetchone()
        return User(*row) if row else None             # *row แตก tuple เป็น 3 argument
    finally:
        cursor.close()

class EmployeeService:
    def __init__(self, conn): self.conn = conn
    def get_employee(self, user, employee_id):
        if has_permission(user, "salary:view"):
            query = "SELECT id, name, position, salary FROM employees WHERE id = %s"
        else:
            query = "SELECT id, name, position FROM employees WHERE id = %s"
        cursor = self.conn.cursor()
        try:
            cursor.execute(query, (employee_id,)); return cursor.fetchone()
        finally:
            cursor.close()
    def update_salary(self, user, employee_id, new_salary):
        if not has_permission(user, "salary:update"):      # เช็กก่อนแตะ DB
            raise PermissionError("Permission denied: cannot update salaries")
        cursor = self.conn.cursor()
        try:
            cursor.execute("UPDATE employees SET salary = %s WHERE id = %s", (new_salary, employee_id))
            self.conn.commit(); return cursor.rowcount
        finally:
            cursor.close()

เทคนิค code injection ที่ผู้โจมตีแทรก SQL ผ่านช่อง input แล้ว database รันคำสั่งนั้น ทำให้อ่าน แก้ ลบข้อมูล สั่งงานระดับ admin หรือแม้แต่สั่ง OS ได้ ยังเป็น A05

query = ("SELECT * FROM users WHERE username='" + username +
         "' AND password='" + password + "'")
ไล่ทีละขั้น: username = admin' -- , password = anything
"SELECT * FROM users WHERE username='" + "admin' -- " + "' AND password='" + "anything" + "'"
⇒ SELECT * FROM users WHERE username='admin' -- ' AND password='anything'

  2. -- ทำให้ทุกอย่างหลังจากนั้นเป็น comment การเช็ก password หายไป
  3. query เหลือ WHERE username='admin' ⇒ login เป็น admin โดยไม่รู้รหัส

ใน MySQL -- ต้องตามด้วยช่องว่าง หรือใช้ admin'# ก็ได้ผลเหมือนกัน

CAP Theorem: ระบบกระจายรับประกันพร้อมกันทั้งสามไม่ได้ · Consistency = ทุกการอ่านได้ค่าที่เขียนล่าสุด ทุก client เห็นข้อมูลเดียวกัน · Availability = ทุก request ได้คำตอบแม้บาง node ล่ม · Partition tolerance = ระบบทำงานต่อได้แม้ข้อความระหว่าง server หาย · เมื่อเกิด network partition ต้องเลือก C หรือ A · ระวัง: C ใน CAP (ค่าล่าสุด) ไม่ใช่ C ใน ACID (ข้อมูลทำตาม integrity rule)

ACID (RDBMS)

  • Atomicity: ทั้งหมดหรือไม่มีเลย
  • Consistency: integrity rule hold
  • Isolation: transaction พร้อมกันไม่รบกวน
  • Durability: commit แล้วไม่หายแม้ crash

BASE (NoSQL หลายตัว)

  • Basically Available: ตอบได้แม้ล้มบางส่วน
  • Soft state: replica อาจไม่ตรงกันชั่วคราว
  • Eventual consistency: หยุด update แล้ว replica จะตรงกัน

BASE ผ่อน strong consistency เพื่อ availability และ scale ไม่ได้ทิ้ง consistency

ข้อดี NoSQL

Horizontal scaling บนเครื่องธรรมดา · schema ยืดหยุ่นกับข้อมูล semi-structured · ข้อมูลรูปร่างเหมือน object ในแอป · write throughput สูง · ถูกกว่าเมื่อ scale ใหญ่

Trade-offs

ไม่มีภาษามาตรฐานเดียว · วินัยของ schema ย้ายไปอยู่ที่แอป · eventual consistency เขียนโปรแกรมยากกว่า · ข้อมูลซ้ำ (denormalized) ทำให้เกิด update anomaly ได้

Indexing: Single field และ explain

Index ทำให้ค้นเร็ว ลดจำนวน document ที่ต้องสแกน · db.collection.createIndex({ field: 1 }) · single field index สร้างบน field ใดก็ได้รวม embedded field, 1 ascending / −1 descending · ตัวอย่าง: หา user ด้วย email ⇒ db.users.createIndex({ email: 1 }) · โครงสร้างเป็น B-Tree

ไม่มี index

ต้อง collection scan ตรวจทุก document ทีละตัวว่า age = 25 ไหม เหมือนอ่านหนังสือทั้งเล่มเพื่อหาคำเดียว

(1) Index lookup ใน index ของ age ที่เรียงแล้ว หา "25" ทันที (2) index ชี้ตำแหน่ง document ที่ตรง (3) ดึงเฉพาะ document เหล่านั้น

Compound Index และ ESR Rule

Index บนหลาย field · ลำดับ field สำคัญ · ใช้กับ query ที่ใช้ทุก field หรือบางส่วน · เช่น createIndex({ lastName: 1, firstName: 1 }) เรียงตามนามสกุลแล้วชื่อ

db.users.createIndex({ status: 1, age: 1 })
db.users.find({ status: "active", age: { $lt: 30 } })   // ใช้ index ได้ทั้งสอง field ⇒ Alice
ESR: Equality → Sort → Range
db.users.find({ status: "active", age: { $gt: 30 } }).sort({ name: 1 })
//                E: status ตรงค่า     R: age เป็นช่วง          S: sort ด้วย name
db.users.createIndex({ status: 1, name: 1, age: 1 })   // เรียง E, S, R

E มาก่อนเพราะตัดข้อมูลให้เหลือกลุ่มเดียว · S มาก่อน R เพื่อให้ผลออกมาเรียงจาก index เลยไม่ต้อง sort ในหน่วยความจำ · R ไว้ท้าย

Prefix rule: index { status, name, age } ใช้กับ query ที่มีแค่ status หรือ status + name ได้ด้วย (แต่ใช้กับ name อย่างเดียวไม่ได้ เพราะไม่ได้เริ่มจาก field แรก)

db.articles.createIndex({ content: "text" })

db.users.find({ tags: "sports" })               // ⇒ John, Alice, Charlie

SQL

SELECT major,
       COUNT(*) AS n,
       AVG(gpa) AS avgGpa
FROM students
WHERE age >= 20
GROUP BY major
HAVING COUNT(*) > 10
ORDER BY avgGpa DESC;

MongoDB

db.students.aggregate([
  { $match: { age: { $gte: 20 } } },
  { $group: {
      _id: "$major",
      n: { $sum: 1 },
      avgGpa: { $avg: "$gpa" } } },
  { $match: { n: { $gt: 10 } } },
  { $sort: { avgGpa: -1 } }
])
อ่าน pipeline ทีละ stage

$match กรองอายุ ≥ 20 (WHERE) → $group จัดกลุ่มด้วย major: _id คือค่าที่ใช้จัดกลุ่ม, $sum: 1 นับ document, $avg: "$gpa" เฉลี่ย (ใส่ $ หน้าชื่อ field เพื่ออ้างค่า) → $match หลัง group = HAVING → $sort −1 = DESC

ตัวอย่างกับ users: aggregate([{ $group: { _id: "$status", n: { $sum: 1 } } }]) ⇒ { _id: "active", n: 3 }, { _id: "inactive", n: 2 }
